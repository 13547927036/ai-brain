## M0 · 渲染后端选型

**问题**：Canvas2D 在 750×1334、数百个精灵的场景下够不够快？

**做法**：写一个只测绘制的基准（`src/render/bench.ts`），同一份精灵数据分别跑
Canvas2D 和 WebGL 两个后端，固定种子、固定数量、各跑数秒取均值。

**结果**（Chrome 155，500 sprite，seed 20261022）：

| 后端 | 帧率 | draw call |
|---|---|---|
| Canvas2D | 564.5 fps | 500 |
| WebGL | 10,619.5 fps | 1 |

**决策**：上线目标是 WebGL；但**原型阶段先用 Canvas2D**。理由是原型要验证的是手感，
Canvas2D 有 564fps 的余量（60fps 的 9 倍），且省掉图集打包与着色器调试。
`render/` 是可替换层，换回 WebGL 不影响 `core/`。

记录见 `m0-result.md`。

## M1 · 内容层 + 战斗核心

**原则**：`content/` 只有数据，`core/` 只有纯逻辑，两者都不碰 DOM。
这条约束由 `tools/check-boundaries.mjs` 在测试之外强制检查。

**落地内容**

- `content/`：8 武器、3 敌人、12 波、3 角色、24 道具、主题色板
- `core/world.ts`：世界状态 + 稠密对象池（敌人 120 / 子弹 200 / 掉落 80）
- `core/formulas.ts`：护甲、闪避、冷却、移速、暴击、经验曲线
- `core/systems/`：移动、索敌、开火、伤害、碰撞、拾取、特效、敌人 AI
- `core/tick.ts`：固定 60Hz 步长 + 累加器，与渲染解耦

**关键决策**

- 固定步长（`LOGIC_DT`）+ `FixedStepper`：保证不同帧率下逻辑一致，
  也保证回放/测试可复现。
- 对象池不扩容：帧时间可预测，池满时丢弃而不是卡顿。

**验证**：`tick.test.ts`、`systems.test.ts`、`pool.test.ts`、`formulas.test.ts`。

## M2 · 构筑循环

**落地内容**

- `core/shop.ts`：4 货位、重掷、锁定、购买、同名同品质合成升阶
- `core/upgrade.ts`：升级三选一，品质权重 0.6 / 0.3 / 0.1
- `core/run.ts`：`battle → levelUp → shop → battle` 状态机，第 12 波通关判定
- `core/save.ts`：局内快照 + 局外记录
- `platform/browser/audio.ts`：程序化 WebAudio 合成，无音频资源文件

**偏离文档之处**（详见 spec 第 0 节）

- 材料掉落 1 → 2：实测经济过紧，武器槽填不满
- 角色「幸运 +50%」实现为属性获取倍率（基础幸运为 0，直接乘无意义）
- 材料与经验合并为一次拾取（否则小八的 +25% 要实现两套链）

**存档的两个设计点**

1. **战斗中存档记为「上一波已完成」**：那一波没打完，若记成已完成，
   恢复后会跳过该波并白拿一次商店。存 `waveIndex = 当前波 - 1`，恢复后重打该波。
2. **严格校验，损坏即作废**：存档是持久化数据，可能被手改或跨版本。
   逐字段校验版本号、波次整数性、数值有限性；任何不符返回 `null` 走新开局。

**验证**：`shop` / `run` / `save` 测试；`runWaveToCompletion` 跑通 12 波。

## M3 · 表现层

**落地内容**

- `render/renderer.ts`：世界渲染（主题色驱动，换皮只改数据）
- `render/ui.ts` + `render/screens.ts`：HUD、商店、升级、结算、选角
- `render/viewport.ts`：逻辑坐标 → 设备像素的等比缩放 + 居中留边
- `app/main.ts`：固定步长主循环，输入 → 逻辑 → 渲染

**为什么需要 `viewport.ts`**：`Renderer` 和 `UI` 原本各自算 `canvas.width / 750`。
浏览器画布恰为 750:1334 等比，看不出问题；但微信主画布铺满屏幕，比例不同，
只按宽度缩放会把画面横向拉扁。抽成共享函数后两端一致，也避免 HUD 与场景错位。

**验证方式（重要）**

模型看不了截图，所以渲染正确性靠两条替代路径：

1. **桩 canvas 冒烟测试**：用 Proxy 记录所有绘制调用，跑遍所有界面，
   任何 undefined 访问/属性写错都会变成可读堆栈。
2. **像素采样**：`getImageData` 统计颜色种类数。空白画布只有 1 种颜色，
   正常战斗画面有 30+ 种 —— 这是「确实画了东西」的硬证据。

浏览器端到端：第 1 波精确 900 帧结束（15 秒 × 60Hz），
掉血、清场、拾取、`battle → shop` 转换全部正确。

## M4 · 微信小游戏适配层

**做法**：`wx` 作为**参数注入**而不是全局引用，因此适配层能在 Node 里用 mock 测。

**对齐项**（必须与浏览器逐条一致，否则两端手感不同）

| 项 | 值 |
|---|---|
| 摇杆半径 | 90 |
| 点击判定阈值 | 18 |
| 点击坐标 | 按下点，非抬起点 |
| 摇杆归一 | `min(len, 90) / 90` |
| 多点触摸 | 只跟踪第一根手指 |

**平台抽象**

- `Platform.onHide(cb)`：浏览器走 `visibilitychange`，微信走 `wx.onHide`
- `app/platform-select.ts`：启动时检测全局 `wx`，有则走微信实现，
  否则走浏览器 —— **同一份游戏代码两端运行，无需两套入口**
- 音频复用同一套程序化合成，只把 `AudioContext` 换成 `wx.createWebAudioContext`；
  无该能力时降级为静默而不是崩溃

**未验证部分**：没有微信开发者工具。已能构建产物
（`npm run build:wechat` → `wechat/dist/`），适配层逻辑有 15 个 mock 测试覆盖，
但**真机运行未验证**。可能踩的坑：`wx.createWebAudioContext` 兼容性、
触摸坐标语义、ESM 在小游戏里的加载方式。
